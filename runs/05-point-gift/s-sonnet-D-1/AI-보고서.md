## 2. 기획서 해석과 스스로 정한 것
- **수수료**: 보강 사항 1번대로 10,000P 이하 500P, 100,000P 이하 1,000P입니다. 100,000P 초과는 `amount/1000` 을 10P 단위로 내림하고 최대 5,000P로 제한합니다(345,670P 는 340P).
- **보내는 사람**은 금액+수수료를 내고, 받는 사람은 금액 전액을 받습니다. 잔액 확인도 금액+수수료 기준입니다.
- **1일 한도**: 오늘 성공한 선물 금액 합계(수수료 제외)와 이번 금액의 합이 1,000만P 이하면 허용합니다. "오늘"은 서버 기본 시간대의 날짜입니다. 한도는 보낸 사람 기준입니다.
- **최소 금액**: 1,000P 미만은 거부합니다.
- **충전**: 1P 이상 1억P 이하입니다. 이 상한은 제가 정했고 기획서에는 없습니다.
- **동시성**: 보내는 사람과 받는 사람의 회원 행을 id 순서로 비관적 잠금한 뒤 한도, 잔액, 차감을 처리합니다. 서로 맞교환해도 데드락이 나지 않고, 처음 쓰는 회원의 포인트 계좌 중복 생성도 막습니다. 실패하면 트랜잭션이 롤백되어 어떤 잔액도 바뀌지 않습니다.
- **오류 코드**(`resultCode`, HTTP 상태는 앞 숫자)
  - `400-3`: 충전 금액 범위 오류
  - `400-4`: 최소 금액 미달
  - `400-5`: 한도 초과
  - `400-6`: 자기 자신에게 선물
  - `400-7`: 잔액 부족
  - `404-2`: 없는 아이디
  - 필드 누락은 기존 방식대로 `400-1` 입니다.
- **포인트 계좌**: 잔액 조회는 계좌가 없으면 0을 돌려주고 계좌를 만들지 않습니다. 계좌는 충전하거나 선물을 받을 때 만들어집니다.

## 4. 남은 문제나 위험
- 포인트 계좌가 있는 회원도 로그인한 사용자 정보에는 잔액이 들어가 있지 않습니다. 잔액은 항상 `GET /api/v1/points` 로 조회합니다.
- 충전 API 가 인증만 되면 누구나 호출할 수 있습니다. 기획서의 "테스트용" 충전이라 그대로 뒀으니 운영 전에 제거하거나 막아야 합니다.
- 회원 행을 잠그는 방식이라, 한 회원이 몰리는 경우(인기 회원이 선물을 많이 받을 때) 같은 회원끼리 직렬화되어 처리량이 떨어집니다.
- 이체 내역 조회 API, 수수료 수익 집계, 취소/환불은 기획서에 없어 만들지 않았습니다. 수수료는 `PointTransfer.fee` 에 기록만 합니다.
