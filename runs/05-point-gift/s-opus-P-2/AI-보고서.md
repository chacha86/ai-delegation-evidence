# 포인트 선물하기 구현 보고서

포인트 선물하기 기능을 만들어 `point gift`로 커밋했습니다(`7875c9b`). 테스트는 기존 37개와 새로 만든 31개가 모두 통과합니다. 15:25에 시작해 약 29분 걸렸습니다.

**먼저 결정이 필요한 것:** 수수료 정책을 기획서 문구 그대로 만들었더니, 10만P를 조금 넘는 선물은 수수료가 오히려 줄어듭니다. 100,000P는 1,000P인데 100,010P는 100P입니다. 100,001P부터 999,999P까지 이렇게 되고, 수수료를 아끼려고 금액을 조금 올려 보내는 일이 생길 수 있습니다. 기획 담당자에게 "10만P 초과 구간은 최소 1,000P"인지 확인하는 것이 좋겠습니다. 바꾸게 되면 `PointPolicy.calcFee` 함수 한 곳만 고치면 됩니다.

## 1. 만든 것

**API** (인증은 기존 방식 그대로입니다)
- **잔액 조회** `GET /api/v1/points`: 성공하면 200과 `{memberId, username, balance}`를 돌려줍니다.
- **테스트용 충전** `POST /api/v1/points/charge`: 성공하면 200과 `data.chargedAmount`, `data.balance`를 돌려줍니다.
- **선물하기** `POST /api/v1/points/transfer`: 성공하면 200과 `data.transferId`, `toUsername`, `amount`, `fee`, `totalDeducted`, `balance`를 돌려줍니다.

## 2. 기획서 해석 (애매했던 곳과 스스로 정한 것)

- **수수료 구간:** "1만P까지", "10만P까지"는 그 금액을 포함한다고 봤습니다. 10만P 초과는 금액의 0.1%에서 10P 미만을 버리고, 최대 5,000P입니다.
- **수수료 부담:** 보내는 사람 잔액에서 금액과 수수료를 함께 빼고, 받는 사람은 금액만 받습니다. 잔액 부족 여부도 금액과 수수료를 합쳐서 판단합니다.
- **수수료가 쌓이는 곳:** 기획서에 없어서 별도 계정에 넣지 않고 선물 기록에만 남겼습니다. 모든 선물이 한 계정을 동시에 고치면 처리가 그 계정에서 막히기 때문입니다. 운영비 집계는 기록을 합산하면 됩니다.
- **1일 한도:** 수수료를 뺀 선물 금액의 합으로 셉니다. 정확히 1,000만P까지는 됩니다. "하루"는 한국 시간 자정부터 자정까지로 정했습니다.
- **최소 금액:** 1,000P부터 선물할 수 있습니다.
- **자기 자신 판단:** 아이디와 회원 번호를 모두 비교합니다.
- **검사 순서:** 최소 금액, 자기 자신, 받는 사람 존재, 1일 한도, 잔액 순입니다.
- **금액 형식:** 정수만 받습니다. 그냥 숫자 타입으로 받으면 1000.5가 조용히 1000으로 잘리기 때문에 소수를 거절하도록 했습니다.
- **충전 1회 상한:** 기획서에는 없지만 1억P로 정했습니다. 오남용과 숫자 범위 초과를 막기 위해서입니다.
- **잔액 저장 방식:** 회원 테이블과 기존 응답을 건드리지 않으려고 지갑 테이블을 따로 만들었습니다. 지갑은 처음 충전하거나 처음 받을 때 생기고, 지갑이 없으면 잔액은 0으로 보입니다.
- **응답 모양:** 잔액 조회는 기획서가 "응답 JSON에 `balance`"라고 해서 최상위에 `balance`를 두었습니다. 충전과 선물은 기존 관례대로 `resultCode`, `msg`, `data` 형식이라 잔액이 `data.balance`에 있습니다.

## 3. 확인한 방법과 결과

- **기존 테스트:** 시작 전에 돌려 37개 통과를 확인했습니다.
- **전체 테스트(JDK 21, H2):** 68개 중 실패 0개입니다. 동시성 확인 실험을 원복한 뒤에 한 번 더 돌려 같은 결과를 얻었습니다.
- **동시성 테스트가 제대로 검사하는지:** 잔액 잠금을 잠시 빼고 돌렸더니 3개 모두 실패했습니다. 9건만 성공해야 할 선물이 20건 성공하는 식이었습니다. 원래대로 돌려놓은 뒤 다시 통과를 확인했습니다.
- **실제 앱 확인:** localhost:18089에 메모리 DB로 앱을 띄우고 Python으로 호출했습니다. 충전, 선물, 받은 포인트로 바로 다시 선물하기, 자기 자신, 최소 금액 미만, 없는 회원, 잔액 부족, 한도 초과, 로그인 없이 호출을 모두 확인했습니다. 기존 `/members/me`와 `/posts`도 그대로 동작했습니다. 한글 응답이 올바른 UTF-8인지도 확인했습니다.

**확인하지 못한 것**
- 개발용 파일 DB(`db_dev`)에 새 테이블이 자동으로 생기는지는 보지 않았습니다. 메모리 DB로만 띄웠습니다.
- MySQL 같은 실제 운영 DB에서의 잠금 동작은 확인하지 못했고, H2에서만 봤습니다.
- 자정 직전과 직후의 한도 경계는 직접 돌려보지 않았습니다. "어제 기록은 오늘 한도에 들어가지 않는다"만 테스트했습니다.
- 대량 부하 테스트는 하지 않았습니다. 동시 요청은 20건 수준까지만 확인했습니다.

**작업 중 생긴 일:** 앱을 끄려고 `taskkill`을 썼는데, 출력 없이 성공(exit 0)이라고 나오면서 프로세스는 그대로였습니다. 다른 종료 도구로 우회하지 않고, 하네스의 백그라운드 작업 정지 기능으로 제가 띄운 bootRun 작업만 멈췄습니다. 그 뒤 프로세스가 없어지고 포트가 닫힌 것을 확인했습니다. Gradle 데몬은 다른 작업과 같이 쓸 수 있어서 그대로 두었습니다. 상태를 다시 확인하던 명령 하나는 권한 거부로 막혔습니다.

## 4. 남은 문제와 위험

1. **수수료 역전:** 위에 적은 대로 기획 확인이 필요합니다.
2. **충전 API 제한 없음:** 로그인한 회원은 누구나 테스트용 충전으로 포인트를 만들 수 있습니다. 운영에 내보내기 전에 끄거나 관리자 전용으로 바꿔야 합니다.
3. **조회 API 없음:** 수수료 수익 집계, 선물 내역 조회, 취소와 환불은 기획서에 없어서 만들지 않았습니다.
4. **자동 테이블 생성 의존:** 새 테이블은 기존 설정(`ddl-auto: update`)에 기대어 생깁니다. 운영 DB에 반영하려면 별도 마이그레이션 스크립트가 필요합니다.
5. **지갑 생성 시 남는 행:** 지갑을 만드는 부분은 잔액 변경과 별도로 바로 저장됩니다. 그래서 선물이 실패해도 받는 사람에게 잔액 0인 지갑이 생길 수 있습니다. 잔액이 0이라 기능상 문제는 없습니다.
6. **기존 401 응답의 한글 깨짐:** 로그인 없이 호출했을 때 나오는 기존 오류 메시지 한글이 `???`로 깨져 나갑니다. 원래 있던 문제이고, 이번 작업에서는 고치지 않았습니다.
