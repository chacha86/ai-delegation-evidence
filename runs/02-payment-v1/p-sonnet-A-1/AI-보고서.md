### 1. 만든 것

**API**
- `GET /api/v1/wallet`은 `{"balance": n}`을 돌려준다.
- `POST /api/v1/wallet/charge`는 본문 `{"amount": n}`을 받고, 응답은 RsData 안에 `data.balance`가 들어 있다.
- `POST /api/v1/posts`는 `price`를 받는다. 생략하면 0이다.
- `POST /api/v1/posts/{id}/purchase`는 응답 `data.balance`에 구매 후 잔액을 준다.
- `GET /api/v1/posts/{id}/content`는 `{"content": "..."}`를 돌려준다.
- 성공은 모두 200 또는 201이고, 인증은 기존 Bearer 방식 그대로다.

**파일**

모두 `src/main/kotlin/com/rest1/` 아래다.
- 새 파일
  - `domain/wallet/wallet/` 아래 `Wallet`, `WalletRepository`, `WalletService`, `ApiV1WalletController`
  - `domain/post/post/` 아래 `PostPurchase`, `PostPurchaseRepository`, `PostPurchaseService`
  - `global/exception/StrictLong.kt`
  - 테스트 `src/test/kotlin/com/rest1/domain/post/post/controller/ApiV1PostPurchaseTest.kt`
- 수정한 파일
  - `Post`에 `price`를 추가했다.
  - `PostDto`에 `price`를 추가했고, 유료 글은 `content`를 비운다.
  - `PostService.write`에 `price` 인자를 추가했다.
  - `ApiV1PostController`에 구매·열람 엔드포인트와 `price` 처리를 넣었다.
  - `MemberService.join`이 가입할 때 지갑을 만든다.

### 2. 정한 규칙과 이유

- **지갑**
  - 지갑은 `Wallet` 엔티티로 따로 두었다. `Member`를 바꾸지 않으려는 것이다. `Rq.actor`가 DB에서 읽지 않은 임시 `Member`를 만들어서 `Member`에 잔액을 두면 맞지 않는다.
  - 가입 시 잔액 0으로 만든다. 지갑 도입 전에 가입한 회원은 처음 조회할 때 만든다.
- **금액 입력**
  - `amount`와 `price`는 정수만 받는다. Jackson은 `1.5`를 조용히 `1`로 잘라 버리기 때문에, 소수·문자열·범위 초과 정수는 400으로 거절한다.
  - 충전은 1 이상 1억 이하다. `price`는 0 이상 1억 이하이고, 음수는 400이다. 상한은 오버플로를 막으려고 정했다.
- **구매**
  - 차감, 작성자 지갑 입금, 구매 기록이 한 트랜잭션이다. 실패하면 전부 롤백된다.
  - 구매 금액은 작성자 지갑에 들어간다. 그렇지 않으면 돈이 사라지기 때문이다.
  - 잔액이 부족하면 402, 이미 구매했으면 409이고 차감하지 않는다. 무료 글이나 자기 글을 구매하려 하면 400, 없는 글이면 404다.
  - 같은 회원의 동시 요청은 지갑 행 비관적 잠금으로 직렬화한다. 잠금 순서는 id 오름차순이라 서로 사고팔아도 교착이 없다. `(buyerId, postId)` 유니크 제약도 걸었다.
- **열람 (`/content`)**
  - 로그인이 필요하다.
  - 무료 글은 누구나, 유료 글은 작성자나 구매자만 열람한다. 그 외는 403이다.
- **공개 조회에서 본문 숨김**
  - 기존 `GET /posts`와 `GET /posts/{id}`는 인증 없이 본문을 줬다. 그대로 두면 결제와 상관없이 본문이 샌다.
  - 그래서 `price > 0`인 글은 이 두 응답의 `content`를 `""`로 내리고 `price` 필드를 추가했다. 무료 글 응답은 `price` 필드가 늘어난 것 말고는 그대로다.
  - 작성자도 본인 유료 글 본문은 `/content`로 읽는다.
- **수정 API**: 글 수정(`PUT`)은 `price`를 바꾸지 않는다. 요청받은 범위가 아니라서 그렇게 했다.

### 3. 확인한 방법과 결과

- **MockMvc 통합 테스트(새 3개)로 확인한 것**
  - 충전 성공과 잘못된 값 거절(0, 음수, 1.5, 큰 수, 누락, 문자열)
  - 인증 없는 요청은 401
  - 미구매자 403
  - 잔액 부족 402와 잔액 불변
  - 구매 후 정확히 차감되고 작성자에게 입금되는지
  - 구매 후 열람, 중복 구매 409와 추가 차감 없음, 제3자 403
  - 자기 글 구매 400, 무료 글 열람과 구매 시도, 없는 글 404, 잘못된 `price` 400
  - 공개 조회에서 유료 글 본문이 비어 있는지
- 기존 테스트 전체 통과.

**확인하지 못한 것**
- 앱을 실제로 띄워서 HTTP로 호출해 보지는 않았다. MockMvc까지만 했다.
- 동시성(같은 회원의 동시 이중 구매, 동시 충전)은 테스트하지 않았다. 잠금과 유니크 제약 설계로만 보장했고, 실제로 돌려 보지 않았다.
- 파일 DB(`db_dev`)에 기존 데이터가 있을 때 `price` 컬럼이 자동으로 추가되는지는 확인하지 않았다. `default 0`을 줬을 뿐이다.

### 4. 남은 문제나 위험

- 지갑이 아직 없는 기존 회원의 지갑을 첫 요청에서 만들 때, 같은 회원의 첫 요청 두 개가 동시에 오면 유니크 제약 때문에 한쪽이 500이 날 수 있다. 신규 가입자는 가입 때 만들어 영향이 없다.
- 환불, 거래 내역, 글 삭제 시 구매 기록 처리는 만들지 않았다. 구매한 글을 작성자가 지우면 구매자 돈은 돌려받지 못한다.
- 유료 글이어도 댓글 API는 그대로 공개다.
- 기존 글 수정 API는 `price`를 못 바꾼다.
- 충전은 결제 수단 연동 없이 호출만으로 잔액이 늘어난다. 요청받은 사양을 그대로 따랐다.
