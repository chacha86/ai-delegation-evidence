### 1. 만든 것
- **지갑**
  - `GET /api/v1/wallet` → `{"balance": N}`
  - `POST /api/v1/wallet/charge` `{"amount": N}` → 200, `data.balance`에 새 잔액
- **글**
  - `POST /api/v1/posts`에 `price`(선택, 생략하면 0)를 추가했다. 0보다 크면 유료 글이다.
  - `POST /api/v1/posts/{id}/purchase` → 200
  - `GET /api/v1/posts/{id}/content` → `{"content": "..."}`
- **파일 (`src/main/kotlin/com/rest1/` 아래)**
  - 새 파일: `domain/payment/` 의 `Purchase`, `PurchaseRepository`, `PaymentService`, `ApiV1WalletController`
  - 수정한 파일: `Member`(balance 컬럼), `MemberRepository`(잔액 증감 쿼리), `Post`(price), `PostDto`, `PostService`, `ApiV1PostController`
  - 새 테스트: `src/test/.../domain/payment/PaymentTest.kt`
- 인증은 기존 방식 그대로다. 새 경로는 기존 `/api/*/**` 인증 규칙이 적용돼 비로그인은 401이다. `SecurityConfig`는 수정하지 않았다.

### 2. 정한 규칙과 이유
- **잔액 저장**
  - 잔액은 별도 Wallet 엔티티 없이 `Member.balance` 컬럼(기본 0)에 둔다. 지갑 행을 늦게 만들 때 생기는 경쟁 상태를 없애기 위해서다.
  - 증감은 조건부 UPDATE(`balance >= 금액`일 때만 차감)로 한다. 동시 요청에도 잔액이 음수가 되지 않는다.
  - 기존 DB에도 `@ColumnDefault("0")` + `nullable=false`로 컬럼이 추가된다.
- **충전**
  - 1 이상 10,000,000 이하의 정수만 허용한다.
  - 0, 음수, 소수(1.5), 문자열, null, 누락, 범위 초과는 400이다. Jackson이 1.9를 1로 조용히 깎는 것을 막으려고 BigDecimal로 받아 직접 검증했다.
  - 잔액 상한은 1조이고, 넘으면 400이다.
- **price**
  - 0 이상 10,000,000 이하의 정수다. 음수, 소수, 초과는 400이다.
  - 글 수정(PUT)으로는 price를 바꾸지 않는다.
- **구매**
  - 구매자 잔액에서 price를 차감하고 같은 트랜잭션에서 작성자 잔액에 입금한다.
  - 잔액 부족은 402, 이미 구매한 글은 409(돈 안 나감), 무료 글과 자기 글은 400, 없는 글은 404다.
  - 차감을 구매 기록보다 먼저 해서 잔액이 부족하면 아무것도 남지 않는다.
  - `(memberId, postId)` 유니크 제약이 동시 중복 구매를 막는다.
- **열람**
  - 무료 글은 로그인한 누구나 볼 수 있다.
  - 유료 글은 작성자와 구매자만 볼 수 있고, 그 외에는 403이다. 관리자도 예외 없이 403이다(운영 정책 확인 필요).
- **공개 조회에서 본문 가림**
  - 기존 `GET /posts`와 `GET /posts/{id}`는 비로그인도 쓰는 공개 API다. 그대로 두면 유료 글 본문이 새므로, 유료 글은 이 두 응답의 `content`를 `""`로 내린다.
  - `PostDto`에 `price` 필드도 추가했다. 무료 글의 응답은 `price` 추가 외에는 그대로다.
- **글 삭제**: 구매 기록은 FK 없이 남기고 환불하지 않는다.

### 3. 확인한 방법과 결과
- **자동 테스트**: `./gradlew test`로 기존 테스트 37개와 새 테스트 3개가 모두 통과했다. 새 테스트는 다음을 확인한다.
  - 초기 잔액 0, 충전, 잘못된 금액 거절
  - 구매 흐름(잔액 부족, 성공, 중복, 열람 권한, 작성자 입금, 비로그인 401)
  - price 검증
- **실제 앱**
  - 실제 앱을 `test` 프로파일(인메모리 DB), 포트 18089로 띄우고 localhost에 Python으로 호출해 확인한 뒤 종료했다.
  - 같은 회원이 같은 글을 동시에 8번 구매했을 때 1건만 성공(200)하고 7건은 409였다. 잔액은 정확히 한 번만 차감됐다.
  - 잔액 100으로 100짜리 글 2개를 동시에 구매했을 때 200 하나와 402 하나였고, 최종 잔액은 0이었다.
  - 공개 조회에서 유료 글 본문이 비어 있고, 구매자만 `/content`를 볼 수 있었다.
- **테스트 격리**: `PaymentTest`는 자체 H2 URL로 별도 컨텍스트를 쓰고 끝나면 닫는다. IDENTITY 값이 롤백되지 않아, 같은 컨텍스트를 쓰면 기존 테스트의 글 id 단언(`4번 게시물`)이 깨졌기 때문이다.
- **확인하지 못한 것**
  - 파일 DB(dev 프로파일)에서 기존 데이터가 있는 상태로 컬럼이 추가되는 마이그레이션은 실행해 보지 않았다. 기본값 0을 지정해 두었을 뿐이다.
  - Swagger 화면, 서로 다른 글을 맞교차로 사고파는 동시 구매는 확인하지 않았다.

### 4. 남은 문제나 위험
- 두 회원이 서로의 글을 동시에 구매하면 이론상 DB 데드락이 날 수 있다. 이 경우 한쪽이 500으로 실패하며 롤백되므로 돈이 틀어지지는 않는다. 구매 요청을 다시 보내면 된다.
- 결제는 내부 포인트 이동만 구현했다. 실제 PG 연동, 환불, 거래 내역 조회는 없다.
- 작성자 본인이 `PUT`으로 유료 글 본문을 바꾸면 이미 구매한 사람에게도 바뀐 본문이 보인다.
- 충전 금액은 요청값을 그대로 믿는다. 서버가 결제를 검증하는 단계가 없다.
