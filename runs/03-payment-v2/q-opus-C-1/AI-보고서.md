## 2. 정한 규칙과 이유
- **잔액은 DB에서 조건을 걸고 한 번에 바꿈.** 충전은 `balance = balance + x`, 차감은 `... WHERE balance >= price`로 처리합니다. 읽은 뒤 계산해서 다시 쓰면 동시 요청에서 충전이 빠지거나 잔액이 음수가 될 수 있기 때문입니다. 차감 결과가 0행이면 잔액 부족(400)입니다.
- **구매 한 건은 트랜잭션 하나.** 구매 기록 저장 → 구매자 차감 → 작성자에게 가격의 90% 적립 순서이고, 하나라도 실패하면 전부 되돌립니다. 동시에 들어온 중복 구매는 유니크 제약에서 막히고 409로 응답합니다.
- **지갑 행은 항상 회원 id 순서로 잠금.** 두 회원이 서로의 글을 동시에 살 때 교착이 생기지 않게 하려는 것입니다.
- **지갑은 처음 충전·구매할 때 만듦.** 생성 경합은 독립 트랜잭션에서 PK 충돌을 무시하는 식으로 처리합니다. 잔액 조회만으로는 지갑을 만들지 않고, 지갑이 없으면 0으로 응답합니다.
- **수수료 = (가격 / 100) × 10.** 가격이 100원 단위라서 정확히 나누어 떨어지고 오버플로도 없습니다.
- **금액은 BigDecimal로 받음.** Long으로 받으면 100.7 같은 소수가 조용히 100으로 잘리기 때문에 소수를 거부하려고 이렇게 했습니다. `amount`가 없거나 null이어도 거부합니다.
- **무료 글(price 0) 구매는 400으로 거부.** 자기 글 구매는 403입니다.
- **잠긴 유료 글은 목록·단건 조회에서 `content: null`, `contentLocked: true`.** 비로그인도 마찬가지입니다. 무료 글을 비로그인에게 보여 주던 기존 동작은 그대로 두었습니다. `/content`는 로그인이 필요합니다(비로그인은 401).
- **관리자도 구매하지 않으면 유료 본문을 볼 수 없음.** 정책에 작성자와 구매자만 볼 수 있다고 되어 있기 때문입니다.
- **가격은 작성 후 바꿀 수 없음.** 글 수정 API는 price를 무시합니다. 이미 산 사람이 있을 수 있기 때문입니다.
- **구매 기록은 글을 외래키로 묶지 않고 id만 저장.** 구매된 글을 작성자가 지워도 삭제가 실패하지 않고, 결제 기록은 남게 하려는 것입니다.

## 3. 확인한 방법과 결과
- **전체 테스트:** 58개 모두 통과.
- **추가 테스트 `PaymentEdgeCaseTest`:**
  - 충전 금액 경계값: 1·100,000은 성공, 음수·100,001·소수·누락은 거부
  - 가격 경계값: 생략·0·100·2500은 성공, 150·100.5는 거부
  - 비구매자·비로그인에게 목록·단건·댓글 조회로 유료 본문이 보이지 않음
  - 같은 글 20회 동시 구매 → 성공 1건, 차감 1회, 작성자 적립 90% 1회
  - 300원으로 100원 글 10개 동시 구매 → 정확히 3개 성공, 잔액 0
  - 지갑이 없는 상태에서 20회 동시 충전 → 누락 없음
  - 두 회원이 서로의 글을 동시에 구매 → 교착 없음
- **로그로 확인한 것:** 중복 구매 18건은 유니크 제약에서, 지갑 생성 경합 1건은 PK에서 막혔습니다. 처리되지 않은 500 응답은 없었습니다.
- **기존 DB 마이그레이션:** 원래 코드로 임시 H2 DB를 만든 뒤 새 코드를 같은 DB에 띄워 Python으로 호출했습니다. 기존 글이 price 0(무료)으로 변환되었고, 충전·구매·중복 구매 409·열람 403/200·구매된 글 삭제가 모두 정상이었습니다. 띄운 java 프로세스는 모두 종료했고(남은 것 0개) 임시 파일도 지웠습니다.
  - 중간에 스크립트 오류로 앱 프로세스 하나(PID 46740)가 남았는데, 직접 띄운 것이라 종료했습니다.

**확인하지 못한 것**
- MySQL 같은 실제 운영 DB에서의 동작. H2(MySQL 모드)에서만 확인했고, 특히 지갑 생성용 `INSERT ... SELECT ... FROM DUAL WHERE NOT EXISTS`는 H2에서만 검증했습니다.
- `balance >= 0` CHECK 제약이 DDL에 실제로 들어갔는지. 로그에서 찾지 못했습니다. 이 제약은 보조 장치이고, 실제로 음수를 막는 것은 조건부 차감입니다.
- 20건을 넘는 고부하 상황과 H2 잠금 대기 시간 초과 시의 동작. 이 경우 409를 주도록 처리는 해 두었지만 직접 일으켜 보지는 못했습니다.

## 4. 남은 문제와 위험
- **유료 글에 대한 클라이언트 영향.** `PostDto.content`가 이제 null일 수 있습니다. 응답에 `price`, `contentLocked` 필드도 늘었습니다. 기존 테스트는 영향이 없지만 프론트엔드는 확인이 필요합니다.
- **글 삭제와 구매가 동시에 일어나는 경우.** 구매 직전에 글이 삭제되면 돈이 결제될 수 있습니다. 글 행을 잠그지 않았기 때문입니다.
- **환불·출금, 구매 내역 조회 API는 없습니다.** 구매한 글이 삭제돼도 환불되지 않습니다.
- **DB 스키마 변경을 `ddl-auto: update`에 맡김.** 새 테이블과 `price` 컬럼(기본값 0)이 자동으로 생깁니다. 운영 환경이라면 별도 마이그레이션 스크립트가 필요합니다.
- **가격 상한이 없습니다.** 실제로 살 수 없는 큰 금액의 글도 만들 수 있습니다.
- **차단된 명령은 없었습니다.** 그 밖에 `rg`가 없어 grep이 기본 동작으로 돌아간 것 말고는 문제가 없었습니다.
