# q-sonnet-B-1 — AI 가 작업 후 낸 보고서 (원문)

유료 글 결제 기능을 구현해 `payment feature` 메시지로 커밋했다(4a20b07). 시작 03:08, 90분 제한 안에 끝냈다. `./gradlew test` 는 전체 45개 통과했다(기존 37개 + 새 8개). 막힌 명령은 없었다.

## 1. 만든 것
**API**
- `GET /api/v1/wallet` → `{"balance": n}`
- `POST /api/v1/wallet/charge` `{"amount": n}` → 200, 충전 후 잔액을 `data.balance` 로 준다.
- `POST /api/v1/posts` 에 `price` 추가(생략하면 0).
- `POST /api/v1/posts/{id}/purchase` → 200, `data.balance` 는 구매 후 구매자 잔액이다.
- `GET /api/v1/posts/{id}/content` → `{"content": ...}`

**파일** (`src/main/kotlin/com/rest1/` 아래)
- 새 파일: `domain/wallet/` 의 `entity/Purchase.kt`, `repository/PurchaseRepository.kt`, `service/WalletService.kt`, `controller/ApiV1WalletController.kt`. 테스트는 `src/test/kotlin/com/rest1/domain/wallet/PaymentTest.kt`.
- 수정: `Member`(balance 필드), `MemberRepository`(행 잠금 조회), `Post`(price), `PostService`, `PostDto`, `ApiV1PostController`, `Rq`(`actorOrNull`), `GlobalExceptionHandler`(DataIntegrityViolation → 409).

**기존 응답 변화**: `PostDto` 의 `content` 가 `String?` 이 되었고 `price`, `locked` 필드가 늘었다. 기존 필드는 그대로이고, 접근 권한이 없는 유료 글의 `content` 만 `null` 이다.

## 2. 정한 규칙과 이유
- **잔액 저장**: 회원 행에 두고, 충전·구매 때 구매자와 작성자 행을 id 오름차순으로 비관적 잠금한다. 동시 충전이 누락되지 않고, 같은 구매자의 동시 요청이 직렬화되며, 서로 교차 구매해도 교착이 생기지 않는다.
- **중복 구매 방지**: 잠금 안에서 구매 기록을 확인하고, `(postId, buyerId)` unique 제약도 추가로 걸었다. 어느 쪽에 걸려도 돈은 한 번만 빠진다.
- **트랜잭션**: 구매는 한 트랜잭션이다. 실패하면 차감·입금·구매 기록이 함께 롤백된다.
- **수수료**: 작성자 수입은 가격 − 가격×10%/100 이다. 가격이 100원 단위라 항상 정수로 떨어진다.
- **무료 글**: 구매하면 400으로 거부한다. 의미 없는 결제와 구매 기록을 막으려는 것이다.
- **가격**: 작성 후 바꿀 수 없다. PUT 은 title/content 만 받으므로 구매 후 가격을 바꾸는 속임수가 불가능하다.
- **열람 제한**: 글 목록·단건·`/content` 모두 같은 규칙을 쓴다. 유료 글 본문은 작성자와 구매자에게만 나가고, 비로그인과 제3자에게는 `content: null`, `locked: true` 다.
- **무료 글 본문**: 기존 목록·단건이 비로그인 공개(`permitAll`)였고 기존 동작을 유지해야 하므로 거기서는 계속 보인다. `/content` 는 로그인이 필요하다.
- **오류 코드**:

| 상황 | 코드 |
|---|---|
| 충전 금액 범위 위반(1 미만 또는 100,000 초과) | 400-3 |
| 가격 규칙 위반 | 400-4 (`price` 가 음수인 경우는 검증기가 먼저 걸러 400-1) |
| 무료 글 구매 | 400-5 |
| 잔액 부족 | 400-6 |
| `amount` 누락·형식 오류 | 400-1 / 400-2 |
| 작성자 본인 구매 | 403-3 |
| 열람 권한 없음 | 403-4 |
| 중복 구매 | 409-1 |
| 없는 글 | 404 |
| 비로그인 | 401 |

## 3. 확인한 방법과 결과
`PaymentTest` 는 MockMvc 로 실제 요청 경로를 타고, 트랜잭션 롤백 없이 회원을 새로 만들어 쓴다.
- **충전·가격**: 충전 0·음수·100,001·문자열·본문 누락 거부 후 잔액 그대로, 100,000과 1은 허용, 잔액 초기값 0, 가격 150·99·-100 거부, 0·100·2500·생략 허용.
- **구매·열람**: 잔액 부족 시 실패, 성공 시 구매자 −2500 / 작성자 +2250, 2회차 409 후 잔액 그대로, 작성자 본인 구매 실패, 작성자는 구매 없이 열람 가능. 비로그인·제3자·구매 전 구매자는 목록·단건·`/content` 어디서도 본문이 안 나오고, 구매 후 구매자에게만 보인다. 무료 글 열람과 구매 거부도 확인했다.
- **동시성**: 20개 동시 충전은 합계가 정확했고, 같은 글 10개 동시 구매는 1건만 성공했다. 3000원으로 1000원짜리 5개를 동시에 사면 3개만 성공하고 잔액은 0이었다. A↔B 교차 동시 구매는 교착 없이 정확히 처리됐다.

**확인하지 못한 것**
- 실제 서버를 띄워 HTTP 로 호출해 보지 않았다. 테스트는 MockMvc 로만 돌렸다.
- 기존 `db_dev` 파일 DB 에 `ddl-auto: update` 로 컬럼이 추가되는 과정은 실행하지 않았다. 컬럼에 `default 0 not null` 을 줬으므로 기존 행은 문제없을 것으로 본다.
- H2 이외의 DB 와 다중 인스턴스 환경은 확인하지 못했다.

## 4. 남은 문제와 위험
- 글을 삭제해도 `Purchase` 기록은 남고 환불도 없다. 환불·취소 기능은 범위 밖이라 만들지 않았다.
- 작성자가 글 내용을 수정(PUT)하면 이미 산 구매자에게도 수정본이 보인다.
- 잔액에 상한이 없다. 오버플로는 `addExact` 로 예외가 나게 했지만 별도 오류 코드는 없다.
- 구매 기록은 `postId`·`buyerId` 를 Long 으로만 갖고 외래키가 없다.
- 구매 응답 코드는 200 이고(201 아님), 중복 구매는 409 다. 클라이언트가 다른 코드를 기대하면 조정이 필요하다.
