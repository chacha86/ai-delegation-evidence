# AI에게 그냥 맡기면 될까? — 46번 맡겨 보고 채점한 결과

> **한 줄 요약**
> AI는 기획서에 **적힌 것**은 잘 만듭니다. **적히지 않은 것**은 그럴듯하게 채우거나 빠뜨리고, 그래도 "다 됐습니다"라고 말합니다.
> 그래서 개발자의 일은 **AI가 모르는 기준을 건네고, 그 기준으로 확인하는 것**입니다.

---

## 이 글에서 처음 나오는 말

| 말 | 무엇인가 | 여기서 왜 필요한가 | 비유 |
|---|---|---|---|
| Opus · Sonnet · Haiku | Anthropic의 AI 모델 3종. Opus가 가장 크고 비싸고, Haiku가 가장 작고 쌉니다. | 같은 일을 세 모델에 맡겨 차이를 봤습니다. | 경력 10년 · 5년 · 1년 차 개발자 |
| 숨긴 테스트 (인수 테스트) | AI에게 **보여 주지 않고** 채점에만 쓴 테스트. 실제 서버를 띄우고 HTTP로 호출해 결과를 확인합니다. | AI가 "통과했다"고 한 것과 실제가 같은지 보려고 썼습니다. | 수험생이 못 보는 채점표 |
| 비관적 락 (`SELECT … FOR UPDATE`) | DB 행을 읽으면서 잠가서, 다른 트랜잭션이 그 행을 못 고치게 하는 방법(JPA `@Lock(PESSIMISTIC_WRITE)`). | 동시에 들어온 송금이 잔액을 덮어쓰지 않게 하려고 AI들이 썼습니다. | 은행 창구에 "사용 중" 팻말 |
| 영속성 컨텍스트 1차 캐시 | JPA가 한 트랜잭션(또는 요청) 안에서 이미 읽은 엔티티를 기억해 두는 저장소. 같은 엔티티를 다시 조회하면 DB 값 대신 기억해 둔 객체를 돌려줍니다. | 이번 실험에서 가장 많이 나온 동시성 버그의 원인입니다. | 메모해 둔 옛 잔액을 보고 계산하는 직원 |
| OSIV (Open Session In View) | 스프링이 HTTP 요청 하나가 끝날 때까지 영속성 컨텍스트를 열어 두는 설정(기본값 켜짐). | 서비스 코드를 직접 부르는 테스트와 HTTP로 부르는 실제 요청의 동작이 달라지는 이유입니다. | 손님이 나갈 때까지 메모장을 덮지 않는 창구 |
| 조건부 UPDATE | `UPDATE … SET balance = balance - 100 WHERE balance >= 100` 처럼 읽기와 쓰기를 쿼리 한 줄로 끝내는 방법. | 락 없이도 동시성 문제를 피한 구현들이 썼습니다. | 잔액 확인과 출금을 한 동작으로 하는 ATM |

## 어떻게 실험했나

같은 Spring Boot 학습용 프로젝트(회원·글·댓글 API)에 같은 일을 AI에게 맡겼습니다. 바꾼 것은 **AI에게 무엇을 주느냐** 하나입니다.

| 실험 | 맡긴 일 | 비교한 조건 |
|---|---|---|
| ① 마이그레이션 | Java → Kotlin 옮기기 (32파일) | 기존 테스트를 줌 / 안 줌 |
| ② 유료 글 결제 | 지갑 충전 · 유료 글 구매 기능 추가 | 기능만 줌 / 정책을 말로 줌 / 정책 + 예시 테스트 |
| ③ 포인트 선물 | 송금 수수료 규정이 있는 기능 추가 | **기획서 그대로 복붙** / 기획서 + 개발자가 보강한 기준 / "기획서대로 만들어줘" 한 줄 |

- 채점은 AI에게 보여 주지 않은 숨긴 테스트로 했습니다.
- 숨긴 테스트도 믿기 전에 먼저 검증했습니다. 정답 코드로 여러 번 돌려 매번 만점이 나오는지, 일부러 버그를 심었을 때 잡아내는지 확인했습니다.
- 모델 3종 × 여러 조건 × 1~2회, 총 46번 실행했습니다.

## 발견 1. 같은 지시를 줘도 결과는 매번 다르다

결제 기능을 같은 지시로 9번 맡겼더니, 정책에 적지 않은 부분에서 9개 구현이 제각각이었습니다.

| 정하지 않은 부분 | AI들이 고른 답 |
|---|---|
| 잔액을 어디에 둘까 | 지갑 테이블을 따로 / 회원 테이블에 컬럼 추가 |
| 동시성은 어떻게 | 비관적 락 / 조건부 UPDATE / 둘 다 |
| 잔액 부족 응답 코드 | 400 / 402 |
| 못 보는 본문은 | 빈 문자열 `""` / `null` |
| 관리자는 유료 글을 볼 수 있나 | 볼 수 있음 / 없음 |
| 구매자가 있는 글을 삭제하면 | 막음 / 구매 기록까지 같이 삭제 / 기록만 남김 |

같은 모델(Haiku)에 같은 지시를 두 번 줘도, 한 번은 동시성이 깨지고 다른 한 번은 작성자에게 돈을 안 넣었습니다. **한 번 잘 됐다고 다음에도 된다는 보장은 없습니다.**

## 발견 2. 말하지 않은 규칙은 AI가 "그럴듯하게" 채운다

회사 규칙 3개(수수료 10%, 1회 충전 한도 10만 원, 가격은 100원 단위)를 알려 주지 않고 맡겨 봤습니다.

| | Haiku | Sonnet | Opus | 회사 규칙 |
|---|---|---|---|---|
| 수수료 | 없음 (전액 지급) | 없음 | 없음 | **10%** |
| 1회 충전 한도 | 없음 / 10억 원 | 1,000만 원 | 100만 원 | **10만 원** |
| 가격 단위 | 제한 없음 | 제한 없음 | 제한 없음 | **100원 단위** |

- **가장 비싼 Opus도 맞히지 못했습니다.** 알려 주지 않은 걸 맞힐 방법은 없습니다.
- 더 위험한 점: 충전 한도를 **스스로 정해서** 넣었습니다. 코드만 보면 "한도 처리가 돼 있네" 하고 지나가기 쉽습니다.
- 규칙을 **알려 주자**(말로, 또는 말 + 예시 테스트로) 세 모델 모두 지켰습니다(7번 중 7번).

> 상식(잔액이 음수가 되면 안 된다, 같은 글을 두 번 사면 안 된다)은 말하지 않아도 대부분 지켰습니다.
> **반드시 알려 줘야 하는 건 우리 회사에만 있는 규칙**입니다.

## 발견 3. "락 걸었습니다" ≠ 동시성 문제없음

가장 많이 나온 버그입니다. AI 보고서에는 이렇게 적혀 있었습니다.

> "구매자·작성자 지갑을 비관적 락으로 잠가 처리했습니다. (동시 요청은 확인하지 못했습니다)"

숨긴 테스트로 동시에 요청을 보내 보니:

- 잔액 1,000원으로 300원짜리 글 10개를 **동시에** 구매 → **10건 모두 성공, 잔액 700원**
- 10,000P 선물 3건을 동시에 → 보낸 사람은 3건 차감, **받은 사람은 1건만 입금** → 2만P 증발

**원인 — 락을 걸기 전에 같은 엔티티를 먼저 읽었습니다.**

```kotlin
ids.forEach { getOrCreate(it) }   // ① 지갑이 있는지 보려고 엔티티를 먼저 읽음 → 1차 캐시에 저장
return ids.associateWith { walletRepository.findByMemberIdForUpdate(it)!! }
// ② FOR UPDATE 로 잠그긴 하지만, JPA는 1차 캐시에 있던 '옛 잔액' 객체를 돌려줌 → 덮어쓰기
```

같은 증상(동시 요청 시 잔액 덮어쓰기)이 Haiku, Sonnet, Opus 모두에서 나왔고, 코드를 열어 원인을 확인한 경우는 모두 이 패턴이었습니다. **채점용 정답 코드를 만든 강사 쪽 AI도 똑같이 만들었습니다.** 숨긴 테스트가 잡았습니다.

## 발견 4. 테스트를 통과해도 버그는 남을 수 있다

| 상황 | 테스트 결과 | 실제 |
|---|---|---|
| Opus가 동시성 테스트를 직접 만들고, 락을 빼면 실패하는 것까지 확인 | 통과 | **HTTP로 동시에 요청하면 돈이 사라짐** |
| 기능 구현 후 숨긴 테스트 11개 | 만점 | 관리자가 유료 글 본문을 볼 수 있음 (테스트에 그 경우가 없었음) |
| 규칙 추가 후 비교 35건 | 전부 같음 | 예전에 올린 1~99원 글은 구매가 실패 (새 데이터로만 확인함) |
| 숨긴 테스트 첫 버전 | "0원 충전 허용" 버그를 통과시킴 | 잔액만 보고 거부 여부는 안 봤음 |

첫 줄이 핵심입니다. Opus의 동시성 테스트는 받는 사람 잔액까지 꼼꼼히 확인했지만 `pointService.transfer(...)` 처럼 **서비스 코드를 직접 호출**했습니다. 그 경로에는 OSIV가 없어서 1차 캐시 문제가 드러나지 않습니다. 실제 사용자는 **HTTP로** 들어오고, 그 경로에서만 버그가 터졌습니다.

> 테스트는 **적어 둔 경우만**, **돌린 경로에서만** 확인합니다.
> "테스트로 확인했다"는 말을 들으면 **어디서, 어떻게, 무엇을 확인했는지** 물어야 합니다.

## 발견 5. 기준을 건네면 작은 모델도 지킨다

포인트 선물 기획서에는 동시성 이야기가 없었습니다. 그 결과입니다.

| 조건 | 동시성을 스스로 챙겼나 | 실제로 지켰나 |
|---|---|---|
| Haiku · Sonnet, 기획서만 (3회) | 락만 넣고 확인 안 함 | **0 / 3** |
| Opus, 기획서만 (3회) | 3번 모두 테스트까지 직접 작성 | **2 / 3** |
| Haiku · Sonnet, **기획서 + 개발자 보강** (2회) | 예시 테스트가 버그를 잡아 스스로 고침 | **2 / 2** |

개발자 보강은 거창하지 않았습니다. 기획서 뒤에 이런 내용을 붙였습니다.

- 경계값 정하기: "정확히 100,000P면 수수료 1,000P"
- 동시 요청에도 잔액이 음수가 되거나 한도를 넘으면 안 된다
- 실패하면 어떤 잔액도 바뀌면 안 된다
- 위 내용을 확인하는 **예시 테스트 7개**

가장 작은 Haiku도 예시 테스트가 실패하자 **원인(1차 캐시)을 스스로 찾아 고쳤습니다.**

> 좋은 모델에 기대면 결과가 흔들립니다(Opus도 3번 중 1번은 놓쳤습니다).
> 기준을 건네면 결과가 모델에 덜 의존합니다.

## 발견 6. "하지 마"는 지켜지지 않을 수 있다

지시서에 **"이 폴더 밖은 건드리지 마"**를 적었는데, 폴더 밖에 파일을 만든 경우가 4번 있었습니다. 넷 다 같은 실수였습니다. Git Bash 경로(`/c/...`)를 Java가 `C:\c\...`로 읽었습니다.

악의는 없었고 AI가 스스로 보고도 했습니다. 그래도 일은 일어났습니다. 중요한 건 **"하지 마"라고 적는 것보다 못 하게 만드는 것**(권한, 격리된 작업 공간)입니다.

## 그래서 AI에게 일을 맡길 때

**맡기기 전에**
- [ ] 기획서를 그대로 붙여 넣기 전에 **빠진 것**을 찾는다. 동시 요청, 실패했을 때, 경계값, 예외 입력, 기존 데이터.
- [ ] 무엇을 정해야 할지 모르겠으면 AI에게 먼저 묻는다. "이 기능을 만들기 전에 **내가 정해야 할 것**을 질문으로 뽑아 줘." 그리고 **답은 내가 정한다.**
- [ ] 우리 회사 규칙(숫자, 정책)은 반드시 적는다. AI는 짐작할 수 없다.

**맡길 때**
- [ ] 기준을 **말이 아니라 테스트로** 건넨다. 예시 테스트 몇 개가 긴 설명보다 정확하다.
- [ ] 위험한 작업(파일 삭제, 외부 전송, 배포)은 지시가 아니라 **권한으로** 막는다.

**받은 뒤에**
- [ ] "완료했습니다"를 믿기 전에 **보고서의 '확인하지 못한 것'**을 읽는다.
- [ ] "테스트 통과"라고 하면 **어떤 경로로, 몇 건을, 무엇을** 확인했는지 묻는다.
- [ ] 동시성은 **실제 HTTP로 동시에 요청을 보내서** 확인한다. 서비스 단위 테스트만으로는 부족할 수 있다.
- [ ] 정책에 없는 결정(응답 코드, 삭제 정책, 한도)을 AI가 혼자 정하지 않았는지 본다.

## 이 실험의 한계 (정직하게)

- 조건마다 1~3번만 돌렸습니다. "항상 그렇다"가 아니라 **"해 본 곳에서는 그랬다"**입니다.
- 작은 학습용 프로젝트였고 DB는 H2만 썼습니다. 실제 MySQL과 트래픽에서는 다를 수 있습니다.
- 채점용 테스트도 AI(강사 쪽 AI)가 만들었습니다. 버그를 심어 검증했지만, 이 테스트도 모든 경우를 덮지는 못합니다(발견 4 참고).
- 기획서의 모호한 문장은 실험을 위해 일부러 넣었습니다. 예상과 달리 AI들은 모호한 문장을 대부분 회사 의도대로 읽었습니다.

---

> **기억할 문장**
> AI는 모르는 것을 모른다. 그리고 모른다고 말하지 않을 때가 많다.
> 개발자는 **처음에 AI가 모르는 것을 건네고, 끝에 그 기준으로 확인하는 사람**이다.
